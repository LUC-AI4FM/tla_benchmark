The module models a simplified version of Azure Cosmos DB's consistency level semantics, capturing how a single cloud database node responds to read and write requests from one or more clients under five configurable consistency guarantees.

The system has two kinds of processes: a `cosmosdb` process representing the cloud database (process ID 0) and one or more `client` processes (IDs 1..NumClients, constrained to exactly one in the model). Communication happens over FIFO channels indexed by process ID. The database maintains an append-only sequence (`Database`) initialized to `<<0>>`. Each client repeatedly performs a write followed by a read for `MaxNumOp` iterations, tracking a session token (`ses`) and a local read history (`chistory`). Write requests append a value to the database and return an acknowledgment with the new sequence position; read requests are dispatched with the configured `Consistency` level, and the server responds by nondeterministically choosing a database version `k` whose range depends on the consistency level: any version for Eventual or Consistent_Prefix, at or after the session token for Session, within `K` versions of the tail for Bounded_Staleness, and exactly the latest version for Strong.

Five invariants check that the last value read by client 1 is valid under the respective consistency model: Eventual and Consistent_Prefix require the read value to exist anywhere in the database; Session requires it to be at or after the client's session position; Bounded_Staleness requires it to fall within the last `K` entries; and Strong requires it to equal the very latest entry. The temporal specification is a standard safety-only `Init /\ [][Next]_vars` with no fairness or liveness properties.
