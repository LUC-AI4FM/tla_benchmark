The module models the ERC20 token standard from Ethereum (EIP-20), specifically targeting the well-known Approve-TransferFrom double-spend attack, and is designed for model checking with Apalache.

The system is parameterized by a set of addresses (`ADDR`), a set of allowed amounts (`AMOUNTS`), and an initial balance mapping (`INITIAL_BALANCES`). State variables track token balances (`balanceOf`), pairwise spending allowances (`allowance`), a set of pending transactions (`pendingTransactions`), the most recently executed transaction (`lastTx`), and a monotone transaction counter (`nextTxId`). Transactions are tagged variants of three types: `Transfer`, `Approve`, and `TransferFrom`.

The `Init` predicate sets balances to `INITIAL_BALANCES`, all allowances to zero, and the pending set to empty. The `Next` relation nondeterministically either submits a new transaction of any of the three types (adding it to the pending set) or commits one pending transaction of each type. Committing a transaction removes it from the pending set, checks validity conditions (sufficient balance, non-negative value, valid allowance), and updates state accordingly or marks the transaction as failed.

The module defines several properties. `NoNegativeBalances` is a safety invariant asserting balances never go negative. `NoTransferFromWhileApproveInFlight` is an intentionally violated invariant capturing the classic attack: a `TransferFrom` can succeed while a smaller replacement `Approve` is still pending. `NoTransferAboveApproved` is an Apalache trace invariant asserting that the cumulative transferred amount by any spender never exceeds a prior approval covering that sum. `NoTransferFrom` and `NoApprove` are false invariants provided as debugging aids to witness example executions. The bound `Full` limits exploration to traces with at most five submitted transactions.
