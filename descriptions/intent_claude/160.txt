# Specification Request: ERC20 Token Contract Model

## System to Model

I need a formal specification of an ERC20 token contract, which is the standard interface for fungible tokens on Ethereum-compatible blockchains. The model should capture the core token transfer and approval mechanics that allow users to move tokens between accounts, either directly or by delegating spending authority to others.

## Functional Requirements

The system should model:

1. **Token balances**: Each address holds a non-negative balance of tokens. The system starts with some initial distribution of tokens across addresses.

2. **Direct transfers**: An address holder can transfer tokens from their own account to another address, provided they have sufficient balance.

3. **Delegated spending (allowances)**: An address holder can authorize another address to spend tokens on their behalf, up to a specified limit. This creates a two-step process where:
   - The token owner first "approves" a spender for some amount
   - The approved spender can then transfer tokens from the owner's account (within the approved limit)

4. **Transaction processing**: The model should capture how transactions are submitted and executed, tracking which transaction was most recently processed.

## Key Correctness Properties

The specification should enable verification of:

1. **Conservation of tokens**: The total supply of tokens remains constant—tokens cannot be created or destroyed through transfers.

2. **No negative balances**: An account's balance should never go below zero.

3. **Allowance integrity**: A spender cannot transfer more than they have been approved to spend.

4. **Authorization requirements**: Tokens can only leave an account if the owner initiates the transfer directly, or if an authorized spender (with sufficient allowance) performs the transfer.

## Scope

The model should work with a small finite set of addresses (e.g., three participants) to enable exhaustive model checking, while using the full range of integers for token amounts to catch potential overflow or underflow issues.
