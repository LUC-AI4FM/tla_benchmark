# Specification Request: Multi-Chain Client Registry System

## System Overview

I need a formal specification for a blockchain interoperability system that manages client registrations across multiple independent chains. The system tracks which chains have established connections to other chains through "clients," where each client represents a view of another chain's state.

## Core Concepts

The system consists of:
- A fixed set of blockchain networks (chains)
- Each chain maintains its own registry of clients
- Clients are identified by sequential numeric IDs within each chain
- Each client has an associated height value representing the blockchain height it has synchronized to

## Functional Requirements

1. **Chain Structure**: Each chain must maintain:
   - A counter for generating unique client identifiers
   - A mapping from client IDs to their current heights

2. **Client Lifecycle**: 
   - Clients can be created on any chain (allocated the next available ID)
   - Client heights can be updated
   - A "null" or uninitialized state should be distinguishable from active clients

3. **Bounded Resources**: The system must operate within fixed limits:
   - Maximum number of clients that can be created per chain
   - Maximum height value that clients can track

4. **Initial State**: All chains start empty with no registered clients and counters at zero

## Correctness Properties

1. **Type Safety**: The system state must always conform to the expected structure—chains map to valid chain records, client IDs map to valid heights (or null), and counters stay within bounds.

2. **Well-formedness**: All data structures must maintain their invariants throughout execution.

## Parameters

The specification should be parameterized by:
- The set of chain identifiers
- The maximum number of clients allowed per chain
- The maximum client height value

## Notes

This appears to be a foundational model for an IBC (Inter-Blockchain Communication) style system. The current request focuses on the basic state structure and type invariants, with the expectation that client creation and update operations would be added in future iterations.
