# Specification Request: Light Client Detector with Faulty Primary

## System Overview

I need a formal specification for a **light client detector** in a blockchain system that can identify misbehaving (Byzantine) validator nodes. The detector should be able to gather evidence of faulty behavior when a primary node provides incorrect information, while relying on a correct secondary node for cross-checking.

## Context and Setup

The system operates in a distributed blockchain environment with:
- A small network of validator nodes (approximately 3 nodes for verification purposes)
- A light client that synchronizes blockchain state by fetching light blocks from full nodes
- Two peer connections: a **primary** (which may be faulty) and a **secondary** (which is correct)
- A reference blockchain representing the true canonical chain

## Key Parameters

The specification should model:
- **Height-based synchronization**: The light client starts from a trusted height and attempts to verify up to a target height
- **Time-bounded trust**: A trusting period during which validator signatures remain valid
- **Clock drift**: Both assumed maximum drift and actual drift between the light client's local clock and the reference blockchain time
- **Byzantine fault tolerance**: The system assumes fewer than 1/3 of validators may be faulty

## Functional Requirements

1. **Light Block Fetching**: The detector must be able to fetch light blocks from both primary and secondary peers independently
2. **Evidence Creation**: When conflicting information is detected between peers, the system must identify a common trusted height and gather evidence of misbehavior
3. **Iterative Verification**: The detector should systematically try different heights to pinpoint where divergence occurred

## Correctness Properties

The specification must guarantee:

1. **Detection Soundness**: If evidence is produced, it represents genuine misbehavior by faulty validators
2. **Progress**: The detector eventually terminates with either successful verification or evidence of misbehavior
3. **Byzantine Resilience**: The system correctly handles scenarios where the primary provides malicious data while the secondary remains honest

## Scenario Focus

This particular configuration should specifically model the case where:
- The primary peer is **faulty/malicious**
- The secondary peer is **correct/honest**
- The light client must detect the primary's misbehavior and produce valid evidence
