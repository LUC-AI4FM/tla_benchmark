# Specification Request: Blockchain Light Client Verification Protocol

## System Overview

I need a formal specification for a blockchain light client protocol that can securely synchronize with a blockchain without downloading all blocks. The light client should be able to verify blockchain state by fetching and validating "light blocks" (block headers with validator signatures) from peer nodes.

## Core Functionality

The system should model:

1. **Light Client Synchronization**: A light client that starts from a known trusted block at some height and attempts to verify blocks up to a target height by fetching light blocks from a primary peer node.

2. **Clock-Based Trust**: The protocol relies on a "trusting period" concept where blocks are considered trustworthy only within a certain time window. The specification must account for clock drift between the local client clock and real time.

3. **Byzantine Fault Tolerance**: The system operates in an environment where some fraction of validators may be faulty/malicious. The specification should parameterize the ratio of faulty validators.

4. **Peer Correctness**: The primary peer providing light blocks may be either correct (honest) or faulty (Byzantine). The specification should handle both scenarios.

## Key Parameters to Model

- A fixed set of validator nodes
- Starting (trusted) height and target height for synchronization
- Trusting period duration
- Assumed vs. actual clock drift bounds
- Whether the primary peer is correct or faulty
- The fraction of validators that may be Byzantine

## Correctness Properties

The specification must guarantee:

1. **Safety**: If the light client accepts a block as verified, it should be consistent with the actual blockchain (when operating within the fault tolerance assumptions).

2. **Progress Tracking**: The system should track verification progress, including which blocks have been fetched, their verification status, and the latest verified block.

3. **Temporal Validity**: Verification decisions must properly account for the trusting period and clock synchronization assumptions.

## Specific Configuration

For this particular instance, I want to analyze the scenario where:
- There are 5 validator nodes
- The primary peer is **correct** (honest)
- Up to 2/3 of validators may be faulty (this exceeds the typical 1/3 threshold, representing a stress test or attack scenario)
- The system should demonstrate whether safety holds or fails under these conditions
