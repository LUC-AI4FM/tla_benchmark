# Specification Request: Multi-Node Distributed Ledger with Read Consistency

## System Overview

I need a formal specification for a distributed ledger system where multiple nodes can process read and write transactions, with the possibility of ledger branches (forks) occurring due to view changes. The system should model how clients interact with the ledger and how transaction ordering and visibility work across a multi-node environment.

## System Description

The system consists of:
- A distributed ledger that can have multiple branches, representing different nodes or views of the transaction history
- Clients that submit read-write transactions and receive responses
- A mechanism for tracking transaction status (committed, pending, etc.)
- View-based ordering where transactions are identified by their view number and sequence number

## Key Behaviors to Model

1. **Transaction Submission**: Clients can request read-write transactions to be processed
2. **Transaction Responses**: The system responds to transactions with a transaction ID (composed of view and sequence number) and information about what prior transactions were observed
3. **Transaction Status**: Transactions can transition to committed status, and clients receive notifications about status changes
4. **Branching/Forking**: The ledger can have multiple branches representing different views of history, which may occur during view changes in the consensus protocol

## Correctness Properties

The specification should verify:
- **Read consistency**: Transactions that observe certain prior transactions maintain a consistent view of history
- **Linearizability or serializability**: The history of transaction requests, responses, and status updates forms a valid execution
- **Branch consistency**: The relationship between ledger branches and transaction visibility is maintained correctly

## Special Testing Requirement

I need an alternative initial state configuration that starts the system with some transactions already committed, rather than beginning from an empty ledger. Specifically, this should model a scenario where:
- Multiple ledger branches already exist
- Several transactions have already been requested, responded to, and committed
- The system continues execution from this mid-execution state

This alternative starting point is useful for model checking specific scenarios without having to explore all paths from the empty initial state.
