# Specification Request: Type Checker Compatibility for Print Operations

## Goal

Create a test specification that verifies a static type checker (specifically Snowcat) correctly accepts print/debugging statements across all common TLA+ data types, matching the permissive behavior of the TLC model checker.

## System Description

This is not a behavioral system specification but rather a **type system conformance test**. The specification should demonstrate that debugging output operations can be invoked with arguments of any standard TLA+ type without causing type errors.

## Requirements

### Data Types to Cover

The specification must include state components representing each of the following types:
- Strings
- Booleans
- Integers
- Sets (e.g., sets of strings)
- Sequences (e.g., sequences of strings)
- Records with named fields

### Print Operations to Validate

The specification should exercise debugging/print operations in the following scenarios:
1. Printing a value while returning another value of the same type (two-argument print that returns its second argument)
2. Printing with an empty/neutral first argument
3. Printing with a typed variable as the first argument
4. Simple single-argument print that just outputs a value

Each of these print patterns must be tested with every data type listed above.

## Correctness Properties

The primary correctness criterion is **type-checker acceptance**: the specification must pass static type analysis. The behavioral aspect is trivial (the state never changes after initialization), as the purpose is purely to verify that the type checker does not reject valid print statements that TLC would accept.

## Context

This serves as a regression test or compatibility test to ensure that static analysis tools remain aligned with TLC's runtime behavior regarding polymorphic debugging operations.
