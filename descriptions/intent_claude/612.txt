# Specification Request: Byzantine Fault-Tolerant Consensus Protocol

## System Overview

I need a formal specification of a Byzantine fault-tolerant consensus protocol, specifically modeling a Tendermint-style or PBFT-style consensus algorithm where a set of processes must agree on a value despite some processes potentially behaving maliciously.

## System Description

The system consists of multiple processes that communicate through message passing to reach agreement on a proposed value. The protocol operates in rounds, where each round consists of distinct phases or steps. Processes exchange proposals and votes to progressively build agreement, with the protocol designed to tolerate Byzantine (arbitrarily faulty) processes up to some threshold.

### Core Mechanics

- **Round-based execution**: The protocol proceeds through numbered rounds, with processes potentially advancing through multiple rounds before reaching consensus
- **Multi-phase rounds**: Each round consists of distinct steps or phases (such as propose, prevote, precommit in Tendermint-style protocols)
- **Proposal mechanism**: Designated proposers broadcast value proposals, where each proposal includes the value itself and timing/validity information
- **Voting with justification**: Processes vote on proposals, with votes potentially referencing earlier rounds where a value was previously considered valid (the "valid round" concept for vote locking)
- **Value locking**: Once a process sees sufficient support for a value, it may become "locked" on that value, carrying this commitment across rounds

## Key Correctness Properties

The specification must guarantee:

1. **Agreement**: No two correct processes decide on different values
2. **Validity**: If all correct processes propose the same value, then any correct process that decides must decide that value
3. **Termination** (liveness): Under favorable conditions (such as eventual synchrony), all correct processes eventually decide

## Additional Requirements

- The model should capture the essential message types and their contents needed for proposal dissemination and multi-phase voting
- The specification should support reasoning about timing assumptions where relevant to the protocol's progress
- The round and step structure should be explicit to enable verification of round-synchronization properties
