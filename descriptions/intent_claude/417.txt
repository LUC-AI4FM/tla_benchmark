# Specification Request: TLA+ Function Application Semantics Test Suite

## System to be Modeled

A test harness that validates the correctness of function application semantics in TLA+, specifically focusing on how the TLA+ model checker evaluates various forms of function construction, indexing, and modification.

## Goal

Create a specification that serves as a regression test suite to verify that a TLA+ implementation correctly handles function-related operations. The tests should confirm expected behavior for core language features involving functions and records.

## Requirements

The test suite must verify correct behavior for the following function application scenarios:

1. **Basic function indexing**: Functions defined over finite sets should return the correct computed value when indexed by an element of their domain.

2. **Record field access**: Records (functions from field names to values) should return the correct value when accessed by string keys.

3. **Functions over infinite domains**: Functions defined over domains like the natural numbers should correctly compute values when indexed.

4. **Function modification with EXCEPT**: When a function is modified at specific indices:
   - Single modifications should update only the specified index
   - Multiple modifications to different indices should all take effect
   - Multiple modifications to the same index should apply sequentially (last one wins)

5. **Nested function access**: Functions that return functions should support chained indexing to retrieve deeply nested values.

6. **Nested function modification**: EXCEPT expressions that modify nested function structures should correctly update values at specified paths.

7. **Multi-argument functions**: Functions defined over Cartesian products of sets should be correctly indexed using either tuple syntax or comma-separated arguments.

8. **Self-referential modifications**: EXCEPT expressions using the `@` symbol to reference the current value at a position should compute correctly.

## Correctness Properties

Each test case must either pass silently (printing a success message) or fail with an assertion error if the evaluated result does not match the expected value. The specification should be structured so that model checking it exercises all test cases and confirms they pass.
