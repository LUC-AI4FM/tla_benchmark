# Specification Request: Liveness Redundancy Detection in TLA+ Specifications

## System to Model

A minimal state machine that transitions from an initial "off" state to a permanent "on" state. This serves as a test harness for validating tooling behavior around liveness property analysis.

## Goal

Create a simple two-state system that can be used to test whether a TLA+ model checker or analysis tool correctly detects **redundant or equivalent liveness conditions**. The system itself is trivial—the real purpose is to exercise various ways of expressing liveness properties (weak fairness conditions) and verify that appropriate warnings are raised when those conditions are logically equivalent or redundant.

## System Behavior

The system should:
- Start in a single initial state
- Have exactly one possible transition to a final state
- Once in the final state, remain there indefinitely (stuttering)

## Liveness Variations to Test

The specification should define multiple variants of the same system, each expressing liveness (fairness) requirements in different structural forms:

1. **Direct equivalence**: A single fairness condition
2. **Conjunction of identical conditions**: The same fairness requirement conjoined with itself through operator definitions
3. **Quantified equivalence**: A fairness condition universally quantified over a finite set, making it equivalent to a single instance
4. **Superset relationships**: Cases where the declared fairness is strictly stronger than necessary
5. **Inline duplication**: The same fairness condition appearing both as a named operator and inline
6. **Refinement mapping**: A version that refines a more abstract specification

## Correctness Properties and Expected Tool Behavior

The specification should enable testing that analysis tools:
- **Raise warnings** when liveness conditions are logically equivalent to simpler forms (detecting redundancy)
- **Do not raise warnings** when one liveness condition properly subsumes another without exact equivalence
- **Handle refinement relationships** between specifications with liveness conditions

## Additional Requirements

The specification should include a separate abstract module that the concrete specification refines, to test liveness analysis in the context of refinement mappings.
