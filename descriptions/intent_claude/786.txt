# Specification Request: Transactional Key-Value Store with Snapshot Isolation

## System Overview

I need a formal specification for a transactional key-value store that supports concurrent transactions with snapshot isolation semantics.

## System Description

The system should model a key-value store where multiple transactions can execute concurrently. Each transaction should operate on a consistent snapshot of the data, isolated from changes made by other concurrent transactions. The specification needs to capture the core behaviors of starting transactions, reading and writing keys, and handling the interactions between concurrent transactions.

## Functional Requirements

1. **Basic Storage**: The system maintains a persistent mapping from keys to values.

2. **Transaction Management**: 
   - Transactions can be started and should operate independently
   - Each transaction works with its own snapshot of the store taken at transaction start time
   - Transactions can read keys (from their snapshot) and write keys

3. **Write Tracking**: The system must track which keys each transaction has modified during its execution.

4. **Conflict Detection**: The system needs to detect when a transaction attempts to read or write a key that has been modified by another concurrent transaction since the snapshot was taken (write-write conflicts or situations where reads may have missed concurrent writes).

## Correctness Properties

1. **Snapshot Consistency**: Each transaction should see a consistent view of the data as it existed when the transaction began, unaffected by concurrent modifications.

2. **Write Conflict Awareness**: The system should be able to identify when transactions have conflicting writes to the same keys, which would be necessary for implementing proper isolation guarantees.

3. **Read Consistency**: The specification should track when a transaction's reads may have "missed" writes from other transactions, enabling detection of potential isolation violations.

## Scope

The specification should be parameterized by:
- A set of possible keys
- A set of possible values  
- A set of transaction identifiers

The model should be suitable for checking with a small number of keys, values, and concurrent transactions to verify the isolation properties hold.
