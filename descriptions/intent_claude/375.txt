# Specification Request: TLA+ ENABLED Operator Test Suite

## System Overview

I need a formal specification that serves as a **test harness for the TLA+ `ENABLED` operator**. The purpose is to verify that a TLA+ model checker correctly evaluates the `ENABLED` predicate under various conditions and edge cases.

## Background

The `ENABLED` operator in TLA+ tests whether an action (a formula involving primed variables) can potentially be taken from the current state—that is, whether there exists some next state satisfying the action. This is a fundamental operator for reasoning about liveness and possibility in concurrent systems.

## Requirements

### What the Test Suite Must Cover

1. **Basic enabledness checks**: Verify that simple actions assigning concrete values to variables are correctly identified as enabled or disabled.

2. **Stuttering steps**: Test `ENABLED` on actions that leave variables unchanged, particularly with the angle-bracket notation that excludes pure stuttering.

3. **Type flexibility**: Confirm that actions assigning values of different types (e.g., strings to a numeric variable) are still considered enabled from a logical standpoint.

4. **State predicates vs. actions**: Distinguish between formulas that are state predicates (no primed variables) and true actions, verifying correct behavior for both.

5. **Parameterized actions**: Test `ENABLED` on actions defined with parameters, including universal quantification over parameter ranges.

6. **Composite actions**: Verify `ENABLED` evaluation when combined with conjunctions and existing transition relations.

7. **Variable substitution in ENABLED**: Test how `ENABLED` handles formulas where different variables are substituted, particularly when the enabledness depends on which variable is being primed.

### Correctness Properties

The specification must guarantee that:

- All defined test cases pass, confirming the model checker's `ENABLED` implementation matches expected semantics
- Tests run both as state invariants (checked in every reachable state) and as possible transitions (checked during next-state computation)
- Failures are clearly reported with identifying information for debugging

### Execution Model

The system should remain in a simple, stable configuration while the tests execute, allowing the invariant checks to run without complex state space exploration interfering with the test results.
