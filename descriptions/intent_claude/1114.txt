# Specification Request: TCP Connection Establishment Protocol

## System to Model

I need a formal specification of the TCP (Transmission Control Protocol) connection establishment mechanism, commonly known as the "three-way handshake." The model should capture how two network peers establish a reliable connection through the exchange of synchronization messages.

## System Description

The system consists of two communicating peers that can initiate or accept TCP connections. Each peer maintains its own connection state and communicates with the other through an unreliable network that delivers messages asynchronously. The protocol should model the standard TCP state machine transitions involved in opening a connection, including states like listening for connections, sending synchronization requests, and reaching an established connection.

The model should support both:
- **Active open**: A peer initiates a connection attempt
- **Passive open**: A peer listens and waits for incoming connection requests

## Key Requirements

1. **Connection State Management**: Each peer must track its current connection state (listening, synchronization sent, established, etc.) and a transmission control block indicating whether the connection context exists.

2. **Message Exchange**: Peers communicate by sending and receiving TCP control messages (SYN, ACK, SYN-ACK, etc.) through network channels. Messages may be queued and processed asynchronously.

3. **State Transitions**: The specification must capture the valid state transitions for TCP connection establishment, where peers progress through intermediate states until both reach the established state.

## Correctness Properties

1. **Connection Establishment**: If both peers participate correctly in the handshake protocol, they should eventually both reach the established connection state.

2. **State Consistency**: The connection states of the two peers should remain mutually consistent according to the TCP state machine rules.

3. **No Spurious Retransmission** (for bounded checking): Consecutive messages in a peer's incoming queue should not be duplicates, ensuring the model explores distinct protocol behaviors.

## Modeling Constraints

For practical model checking, the specification should be structured to allow verification with a fixed pair of peers, taking advantage of symmetry between the two participants to reduce the state space.
