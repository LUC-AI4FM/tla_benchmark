# Specification Request: Byzantine Fault-Tolerant Consensus Protocol

## System to Model

I need a formal specification of the Tendermint consensus protocol, which is a Byzantine fault-tolerant algorithm used for reaching agreement in distributed systems. The model should capture the core consensus mechanism where a set of processes (some potentially Byzantine/faulty) work together to decide on a value.

## System Description

The system consists of multiple processes that proceed through rounds of consensus. In each round, processes go through distinct phases to propose, vote, and commit values. The protocol must tolerate a bounded number of Byzantine (arbitrarily faulty) processes while ensuring that correct processes eventually agree on the same value.

Key aspects to model:
- **Round-based structure**: Processes advance through numbered rounds, with each round having a designated proposer
- **Multi-phase voting**: Each round involves proposal, prevote, and precommit phases
- **Locking mechanism**: Processes lock onto values under certain conditions to prevent conflicting decisions
- **Valid and invalid values**: The system should distinguish between valid values that can be legitimately proposed and invalid values that only faulty processes would propose

## Configuration Parameters

The specification should be parameterized to allow verification with:
- A fixed number of total processes (e.g., 5 processes)
- A threshold of maximum tolerable Byzantine faults (e.g., 1 faulty process)
- A bounded number of rounds to explore
- A set of possible values (both valid and invalid)
- An arbitrary proposer selection function for each round

## Correctness Properties

The specification must guarantee these fundamental consensus properties:

1. **Agreement**: No two correct processes decide on different values
2. **Validity**: If all correct processes propose the same value, only that value can be decided
3. **Integrity**: A correct process decides at most once

The model should also support collecting evidence of Byzantine behavior for accountability purposes.

## Verification Goals

The specification should be suitable for model checking with bounded parameters to verify safety properties hold even when Byzantine processes behave arbitrarily, including sending conflicting messages or proposing invalid values.
