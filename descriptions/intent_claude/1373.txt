# Specification Request: TLA+ Module Name Resolution and Overloading

## System to Model

A test harness for verifying correct name resolution in TLA+ tooling when one module is instantiated by another, specifically focusing on how identifiers with the same name but different meanings are handled across module boundaries.

## Goal

Demonstrate and verify that the TLA+ model checker correctly distinguishes between identifiers that share the same name but have different roles in different modules. This is particularly relevant when an auxiliary module defines an operator with a name that matches a variable in the parent module that instantiates it.

## Requirements

1. **Constant Parameter**: The module should accept a constant parameter that can be assigned a value (such as 42) when instantiated.

2. **State Variable**: The module should maintain a simple state variable initialized to a known value (such as the string "x").

3. **Name Aliasing**: Define operators that simply reference the variable and constant, giving them names that will conflict with definitions in a parent module that instantiates this one.

4. **Initialization Verification**: The initial state must confirm that:
   - The aliased operator for the variable correctly resolves to the variable's value
   - The aliased operator for the constant correctly resolves to the constant's assigned value

5. **Diagnostic Output**: Print statements should trace the evaluation to help diagnose any name resolution issues.

6. **Trivial Progression**: After initialization, the system should remain unchanged (stuttering behavior only).

## Correctness Properties

- The variable alias must evaluate to the variable's initialized value, not be confused with any same-named entity in an instantiating module
- The constant alias must evaluate to the constant's assigned value
- Name resolution must be consistent and unambiguous within this module's scope
