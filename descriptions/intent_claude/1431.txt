Write a TLA+ specification that demonstrates a subtle pitfall when using state constraints together with liveness properties in TLA+. Model a simple two-state system that cycles indefinitely between states A and B, with weak fairness ensuring the system always keeps making progress. Apply a state constraint that bounds the length of a history log so that model checking remains tractable. Then assert a liveness property claiming the system eventually reaches a "Done" state. The purpose of the module is to illustrate that the liveness property is spuriously reported as satisfied when a state constraint is active: because the constraint artificially cuts off all infinite behaviors that would otherwise witness the property's violation, the model checker cannot find a counterexample even though the system genuinely never reaches "Done" in an unconstrained execution. The key correctness property to check is that the system eventually reaches "Done," which should actually fail without the constraint but appears to pass with it, thereby warning users about the dangers of combining state constraints with liveness checking.
