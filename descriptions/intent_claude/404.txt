# Specification Request: Function Equality Semantics Test Suite

## Goal

Create a formal specification that serves as a test harness to verify that a TLA+ model checker correctly implements equality semantics for functions across their various syntactic representations.

## System Description

The system should be a minimal state machine (essentially a single-state system) whose purpose is to evaluate a series of assertions about function equality at initialization or as an invariant check. The focus is not on modeling dynamic behavior, but on using the model checker's invariant-checking mechanism to validate semantic equivalences.

## Requirements

### Core Verification Goals

The specification must verify that the following representations of functions are treated as semantically equal when they define the same mapping:

1. **Functions defined over explicit sets vs. tuples (sequences)**: A function mapping indices 1 through n should be equal to the corresponding tuple/sequence with the same values.

2. **Functions over differently-ordered domain specifications**: Functions defined over the same set elements but listed in different orders should be equal (since sets are unordered).

3. **Functions over empty domains**: A function with an empty domain should equal an empty sequence.

4. **Multi-argument functions vs. functions on Cartesian products**: A function taking multiple arguments should be distinguishable from or comparable to a function taking a single tuple argument from the Cartesian product of those domains.

5. **Nested functions vs. flat multi-argument functions**: The specification should verify whether a curried/nested function representation equals or differs from a flat multi-argument representation.

6. **Record syntax vs. function syntax**: Functions over string domains should compare correctly with record notation.

7. **EXCEPT modifications**: Functions modified using EXCEPT notation should equal directly-constructed functions with the same resulting values.

### Correctness Properties

- Each equality/inequality test should either pass silently (with optional success logging) or halt with a clear failure message identifying which test failed.
- The test suite should be structured so that all tests are evaluated, and any failure is immediately apparent.

### Output Requirements

- Successful tests should print confirmation messages.
- Failed tests should trigger assertion failures with descriptive error messages indicating which specific test failed.
