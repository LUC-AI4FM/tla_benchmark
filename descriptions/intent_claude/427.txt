# Specification Request: TLA+ Operator Definability Test Suite

## Goal

Create a test specification that verifies the TLA+ language parser and model checker correctly handle user-defined custom operators across all supported operator syntaxes.

## System Description

This is not a model of a distributed system or algorithm, but rather a **language feature test harness** for TLA+ tooling. The specification should exercise the TLA+ parser's ability to:

1. Accept user-defined operators using all available infix, prefix, and postfix operator symbols
2. Parse and evaluate expressions that use these custom-defined operators
3. Execute transitions that invoke each defined operator

## Requirements

### Operator Coverage

The test must demonstrate that users can define their own semantics for:

- **Arithmetic-style infix operators**: addition, subtraction, multiplication, division, exponentiation symbols and their doubled variants
- **Relational-style infix operators**: comparison symbols, subset/superset relations, ordering relations, equivalence relations
- **Logical-style infix operators**: conjunction and disjunction symbols
- **Range operators**: interval notation symbols
- **Special mathematical infix operators**: lattice operations, product operations, similarity relations, proportionality
- **Assignment-style infix operators**: various assignment notations
- **Postfix operators**: closure and modifier suffixes
- **Prefix operators**: negation-style prefix

### Exclusions

The test should note which operator symbols are pre-defined by standard modules and therefore cannot be redefined by users.

### Verification Approach

The specification should structure transitions such that model checking will exercise each custom operator definition at least once, confirming that:

1. The operator definitions are syntactically valid
2. The operators can be invoked in expressions
3. The model checker can evaluate expressions containing these operators

## Correctness Properties

The primary "correctness property" here is implicit: **the specification should parse and model-check without errors**. If any operator syntax is not properly supported, the tooling should fail during parsing or evaluation, thereby revealing the gap in operator support.
