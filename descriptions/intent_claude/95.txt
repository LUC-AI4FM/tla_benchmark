# Specification Request: Configuration Override Testing Framework

## System to Model

I need a simple test harness specification that can verify whether a TLA+ model checker correctly parses and applies configuration settings from different sources (default values, configuration files, and command-line arguments).

## Purpose

The goal is to create a minimal specification that serves as a diagnostic tool for testing configuration precedence in TLA+ tooling. This isn't modeling a real distributed system—it's a meta-level test to ensure that when users specify different initialization predicates, transition relations, or invariants through various configuration mechanisms, the model checker actually uses the intended definitions.

## Requirements

The specification should include:

1. **Multiple initialization options**: Several alternative starting states, each producing a distinct initial value, so that we can verify which initializer was actually applied based on the resulting state space.

2. **Multiple transition options**: Several alternative transition relations that evolve the state differently (e.g., incrementing by different amounts), allowing us to confirm which transition relation is in effect.

3. **Multiple invariant options**: Several safety properties with different bounds, so that some will pass and others will fail depending on which initialization and transitions are active—letting us verify the correct invariant was selected.

4. **Liveness properties**: At least one temporal property to test that liveness checking configuration also works correctly.

## Key Correctness Properties

The specification itself doesn't enforce deep correctness properties about a real system. Instead, the "correctness" being tested is external: does the toolchain respect configuration overrides? The invariants should be designed so that:

- With default settings, certain invariants hold
- With configuration file overrides, different invariants become relevant
- With command-line overrides (highest precedence), yet another set of behaviors should be observable

The specification should be minimal—just enough state to distinguish which configuration was applied.
