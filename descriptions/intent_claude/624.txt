# Specification Request: Byzantine Fault-Tolerant Consensus Protocol

## System Overview

I need a formal specification of a round-based Byzantine fault-tolerant (BFT) consensus protocol, similar to Tendermint or PBFT-style algorithms. The system should model a set of distributed processes that work together to agree on a single value, even in the presence of some number of faulty (potentially malicious) participants.

## Core Requirements

### Participants and Fault Model
- The system consists of a fixed set of processes, some of which may be Byzantine (arbitrarily faulty)
- The protocol must tolerate up to some threshold of Byzantine processes while still guaranteeing safety and liveness

### Round-Based Structure
- The protocol operates in numbered rounds
- Each round proceeds through distinct phases or steps (such as proposal, prevote, and precommit phases)
- Processes may advance through multiple rounds if consensus is not reached in earlier rounds

### Message Types
The protocol should include at least two kinds of messages:
1. **Proposal messages**: Sent by a designated proposer containing a proposed value, along with information about which round the value was previously considered valid (if any)
2. **Vote messages**: Sent by all processes to indicate their support (or lack thereof) for a particular value in the current round

### Validity and Locking
- The protocol should track when a value becomes "locked" or considered valid at a particular round
- A value that was previously supported in an earlier round may carry forward with proof of that earlier support

## Correctness Properties

### Safety
- **Agreement**: No two correct processes should decide on different values
- **Validity**: If a value is decided, it must have been properly proposed

### Liveness (under appropriate conditions)
- **Termination**: Eventually, all correct processes should reach a decision (given sufficient synchrony and fewer than the threshold of Byzantine faults)

## Additional Modeling Considerations

The specification should support:
- Tracing execution history for debugging and verification purposes
- Clear identification of which process sent each message
- Tracking the current round and step for each process
