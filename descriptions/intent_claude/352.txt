# Specification Request: TLA+ Function Definition and Application Semantics

## System to Model

I need a formal specification that serves as a **test suite for TLA+ function semantics**, specifically verifying the correct behavior of function definition, application, and modification operations in the TLA+ language itself.

## Goal

The purpose is to validate that a TLA+ model checker correctly implements the semantics of:

1. **Recursive function definitions** with various parameter patterns
2. **Function application** with different argument-passing styles
3. **The EXCEPT construct** for creating modified copies of functions
4. **Record-valued functions** and nested field access

## Requirements

### Function Definition Patterns
- Functions taking a single integer parameter
- Functions taking multiple parameters of the same type
- Functions with mixed parameter declarations including tuple-destructuring patterns (e.g., accepting a pair and binding its components)
- Functions returning records with named fields

### Function Application Semantics
- Applying functions with arguments listed separately (comma-separated)
- Applying functions with arguments packaged as a single tuple
- Both styles must yield identical results for the same logical arguments

### Function Modification (EXCEPT)
- Creating a modified function that differs at specific argument values
- Chained modifications that update the same position multiple times (later updates should take precedence, but may reference the previous value)
- Modifying nested structure (e.g., updating a specific field of a record that is itself a function's return value)
- The `@` symbol must correctly reference the original value at the position being modified

### Nested Function Structures
- Functions whose values are themselves functions
- Functions returning records, where field access follows function application
- Combining EXCEPT on both the outer function structure and inner values

## Correctness Properties

The specification must verify that:
- Each function application produces the mathematically expected result
- Tuple-style and comma-separated argument passing are semantically equivalent
- EXCEPT modifications affect only the specified positions, leaving other positions unchanged
- Sequential EXCEPT modifications are applied in order, with later modifications seeing earlier ones
- Record field access on function results works correctly
- The `@` reference in EXCEPT correctly captures the pre-modification value at that position
