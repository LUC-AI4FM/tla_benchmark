# Specification Request: TLA+ Operator Override and Replacement Testing

## System Overview

I need a formal specification that serves as a test harness for verifying that a TLA+ model checker correctly handles operator overriding and replacement mechanisms. This is essentially a meta-level test of the tooling's ability to substitute custom implementations for both user-declared operators and built-in operators.

## Core Requirements

### What the System Must Model

The specification should test the model checker's support for:

1. **Constant operator parameters with custom implementations** - The ability to declare operators as module constants and provide concrete implementations at model-checking time.

2. **Infix operator replacement** - Support for user-defined infix operators (using symbolic syntax) that can be given custom definitions.

3. **Built-in operator overriding** - The ability to replace standard library operators (like sequence operations) with custom implementations during model checking.

4. **Local operator definitions with infix syntax** - Support for defining custom infix operators within local scopes using symbolic notation.

### Expected Behaviors to Verify

The test harness must confirm that:

- A binary predicate constant, when instantiated with a set-building function, produces the expected set output
- A custom infix operator constant produces tuple results as configured
- A length-computing operator constant correctly measures sequence length
- An arithmetic operator constant performs addition correctly
- A standard library sequence operator can be overridden with a singleton-set implementation
- A standard library concatenation operator can be overridden with arithmetic addition
- Locally-defined symbolic infix operators work correctly for comparisons

## Correctness Properties

The specification must guarantee:

1. **All operator substitutions behave according to their replacement definitions** - Each overridden or replaced operator must produce results consistent with its configured implementation, not its original semantics.

2. **The system reaches a valid initial state only if all tests pass** - Test failures should be caught via assertions, making invalid substitution behavior immediately detectable.

3. **Trivial safety invariant** - After initialization, the system should maintain a stable state (this is a one-shot test, not an ongoing protocol).
