# Specification Request: TLC Model Value Creation and Comparison Testing

## System Overview

I need a formal specification that serves as a test harness for verifying the behavior of dynamically created model values in the TLC model checker. Model values are special symbolic constants used during model checking, and I want to verify that they can be programmatically generated and that they behave correctly with respect to equality and string conversion.

## Requirements

### Core Functionality

The system should demonstrate the ability to:

1. **Programmatically generate model values**: Create a set of distinct model values by constructing their names from a common prefix combined with numeric suffixes (e.g., generating three model values with names following a pattern like "T_MV1", "T_MV2", "T_MV3").

2. **Maintain a stable collection**: Once the set of model values is created, it should remain unchanged throughout system execution.

### Correctness Properties

The specification must verify:

1. **Cardinality preservation**: The collection of generated model values must contain exactly the expected number of distinct elements.

2. **Membership verification**: Each specifically named model value must be present in the generated collection, confirming that programmatic generation produces the expected values.

### Assumptions to Verify

The specification should also validate fundamental properties of model values through static checks:

1. **String conversion**: Converting a model value to a string should return its name, and this result should be non-empty.

2. **Reflexive equality**: A model value must equal itself.

3. **Distinctness**: Model values with different names must not be equal to each other.

4. **Type safety**: Attempting to compare model values of different types (indicated by different prefixes before the underscore) should produce a specific error, ensuring type discipline among model value families.

## Purpose

This specification acts as a regression test to ensure that the TLC extension for creating model values at runtime works correctly, particularly verifying that generated model values are properly distinguishable, correctly named, and obey expected equality semantics including cross-type comparison restrictions.
