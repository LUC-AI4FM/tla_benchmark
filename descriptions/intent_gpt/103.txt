Model an ERC-20–style token contract plus the external submission and execution of transactions on a blockchain, and specify the safety properties to check for the well-known approve/transferFrom allowance interaction. The model should represent accounts with integer token balances and pairwise allowances that owners grant to spenders. It must allow three kinds of user-initiated operations to be submitted as pending transactions: direct transfers between accounts, approvals that set an allowance for a spender, and transferFrom operations that spend on behalf of an owner according to an allowance. Submissions are recorded and later executed by nondeterministically choosing pending transactions to commit; execution can succeed or fail depending only on the transaction fields and current state (e.g., insufficient balance, insufficient allowance, negative amounts, or other invalid fields), and successful commits update balances and allowances accordingly.

Specify the following correctness requirements as invariants or temporal properties (not as implementation steps):

- No account balance ever becomes negative.
- Approve should overwrite the current allowance for that owner–spender pair; approvals that would set negative allowances are rejected.
- Transfer and transferFrom must only succeed when the initiating constraints hold (sufficient balances, sufficient allowance for transferFrom, non-negative amounts, and distinct addresses where required).
- It must be possible to detect the classic approve/transferFrom race: a transferFrom should never be allowed to succeed in a way that, while an approve for the same owner→spender is still pending that would set a strictly smaller allowance than the transfer amount, results in an unauthorized over-withdrawal. Formulate this as a safety property: any sequence of successful transferFrom executions by a spender from an owner must be covered by a prior approved allowance whose value is at least the sum of those successful transfers that occurred after that approval.
- Provide a bound or liveness assumption to keep the state space checkable (e.g., limit on transaction ids or number of pending transactions).
