Specify a distributed checkpoint coordination system for a replicated state machine cluster that uses a leader to assign checkpointing responsibilities to replicas. The model should describe nodes that can fail and recover, network links that can fail and recover, and a replicated log maintained by each node with monotonically increasing execution counters. The leader must be electable only when it has quorum and is fully caught up (no pending log entries). The leader should be able to propose, via a replicated command recorded in the logs, that a particular non-leader replica take a checkpoint at the current open log index; that proposal must be disseminated to reachable replicas so that a chosen replica can learn it even if it initially missed the message.

Model timeouts and checkpoint leases: a lease associates a node with a log counter and can be replaced when it times out or when the checkpointing node reports progress. A node may mark itself able to take a checkpoint only when it has a valid lease for itself, the leader did not assign someone else, and it is not the leader. A node beginning checkpointing must be mutually exclusive with other nodes doing so; a node taking a checkpoint must eventually either complete or be preempted by timeout or failure. Completing a checkpoint must persist a snapshot (log prefix and counter) and clear the lease.

Specify safety properties: at most one node may be eligible or actively performing a checkpoint at once; the leader never itself takes a checkpoint; leases imply exclusivity; replicated logs never contain conflicting entries. Specify liveness requirements: eventually some node becomes eligible to checkpoint, eligible nodes eventually start checkpointing unless they fail or their lease times out, checkpointing nodes eventually finish or time out, and eventually a non-blank checkpoint is produced. The model should not prescribe implementation details such as specific message formats or those exact state variable names.
