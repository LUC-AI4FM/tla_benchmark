Specify a model of a distributed transactional key-value store with two clients and two keys. The system must support both optimistic and pessimistic transaction styles: one client uses pessimistic locking, the other uses optimistic concurrency control. Transactions may perform reads and writes on subsets of the keys; each client has a defined read-set and write-set. The system must ensure atomicity and isolation of each transaction: a transaction’s reads see either the state before the transaction began or a consistent state reflecting committed transactions, and no two concurrent transactions produce write-write conflicts that violate serializability. Implement a primary (leader) mapping for keys so that each key has an assigned primary replica responsible for coordinating updates; the model should allow transactions to be forwarded to the appropriate primary when necessary. Include message-passing between clients and replicas and allow for retries or aborts of optimistic transactions when conflicts are detected. Specify safety properties: serializability (all committed transactions are equivalent to some serial execution), no lost updates, and preservation of read-your-writes for a client within its own transaction. Also specify liveness requirements: a transaction that repeatedly retries under bounded contention must eventually commit, and the system must make progress when a majority of replicas and communication channels are reliable.
