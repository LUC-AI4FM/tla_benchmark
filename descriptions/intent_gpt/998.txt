Specify a formal model of a centralized resource allocator that manages a fixed finite set of reusable resources and multiple clients. The allocator must permit each client to repeatedly issue requests for a subset of resources, obtain allocations (possibly in multiple partial steps), and later return resources. A client may issue a new request only after its previous request has been fully satisfied and it has no held resources. The allocator maintains and advances a scheduling order over clients with outstanding requests; when choosing which allocations to grant, it may allocate resources out of global order as long as it never gives a resource to a client if some earlier client in the current schedule is still requesting that resource. The allocator may extend the schedule nondeterministically by inserting all currently requesting clients in an arbitrary order.

Model the following obligations and guarantees as correctness properties (safety and liveness):

- Safety: resources are never held concurrently by more than one client (mutual exclusion); a client never holds a resource that is currently requested by any client earlier in the schedule; scheduled clients in the order always correspond to clients that currently have outstanding requests.

- Allocation feasibility: for every scheduled client, every remaining requested resource must be reachable assuming earlier scheduled clients eventually release what they hold.

- Liveness assumptions and guarantees:
  - Clients eventually return all held resources after their request has been fully satisfied.
  - The allocator will eventually make allocation progress: whenever an allocation is possible for some client, the allocator will eventually perform an allocation step for that client.
  - The allocator will eventually schedule any client that currently has an outstanding request.
  - Consequently, every requested resource is eventually allocated to the requesting client, and each client’s requests are satisfied infinitely often.

Do not prescribe an implementation; allow nondeterministic scheduling, partial allocations, and returns, but require the invariants and progress properties above to hold.
