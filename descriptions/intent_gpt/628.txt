Model a light-client block-header verification system that watches multiple full nodes (peers) and must detect and react to equivocation and liveness faults among validators. The system should represent a fixed set of validator nodes, a reference blockchain with monotonically increasing heights and timestamps, and peers that report observed block headers from the chain. Some peers may be faulty and may report conflicting headers for the same height or provide stale information.

Requirements:
- The light client must accept a header only if it receives sufficient supporting votes or signatures consistent with a threshold of honest validators; the acceptance threshold should reflect a specified maximum tolerated faulty fraction.
- The client must detect conflicting evidence: two distinct valid headers for the same height claimed by different peers constitute equivocation and must be reported as evidence.
- The client must ensure safety: it never accepts two incompatible headers at the same height (no double-finalization), even if some peers are faulty.
- The client must ensure liveness under optimistic conditions: if a correct majority (or the non-faulty quorum per the threshold) of peers continuously provide consistent, timely headers, the client eventually accepts new headers up to the latest height.
- Time and trusting period: headers have timestamps; headers older than a configurable trusting period are considered expired and must not be trusted for finalization.
- The model should allow adversarial behavior by faulty peers (e.g., equivocation, omission, or stale replies) and express invariants capturing safety (no two incompatible accepted headers at same height) and progress (eventual acceptance of higher heights when non-faulty quorum is available).
