Specify a formal model of a task orchestration subsystem for a cluster scheduler that manages desired and actual lifecycle states of service tasks distributed across worker nodes. The model should represent services that request either a fixed number of replicas or a global replica per node, and tasks that belong to services and occupy either a numeric slot (for replicated services) or a node (for global services). Tasks have an immutable identity (derived from service, slot/node, and a local task identifier), a current lifecycle state, a desired state set by the orchestrator, and an assignment to a node or an unassigned sentinel.

Model the allocator and reconciler behavior at an abstract level: the system must create, assign, accept, start, run, and end tasks in response to service specifications and desired states, and must remove or mark tasks orphaned when services are removed or when nodes become unavailable. The model must enforce monotonic progress of individual task state transitions (tasks may only move to states that are later in a defined ordering). It must ensure that for each service the number of runnable tasks per replica slot or per-node global replica meets the service’s desired replica count unless constrained by node capacity or removal. Uniqueness of task identities must hold: no two distinct tasks may share the same service+slot/node+local id triple. Specify safety properties: tasks never regress to earlier lifecycle ranks, and at most one running task exists per slot (or per node for global services). Specify liveness goals: if a service desires replicas and resources are available, the system eventually produces runnable tasks to satisfy the desired count; if a service is marked removed, all its tasks eventually reach a terminal removed or shutdown state. Do not prescribe implementation details of assignment or scheduling algorithms, only the allowed state space and the correctness properties above.
