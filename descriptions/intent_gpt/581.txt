Specify a formal model of a single-node transaction processing service that handles read-write transactions, their execution, responses, and the recording of a history of events, suitable for model checking with a bounded event history.

The model should describe a node that receives transaction requests, executes transactions, produces responses to those requests, and emits committed-status responses when transactions have been durably applied. The system must allow multiple transactions to be in flight over time, but the recorded history of observable events must be bounded to a fixed limit for model checking. The model must capture nondeterministic ordering of request arrival, execution, and response emission subject to the usual causal constraints (e.g., a response cannot precede the matching execution).

Key correctness properties to guarantee:
- Safety: every response corresponds to a previously issued request and reflects a legal result of executing that request on a sequential abstract datastore; committed-status responses must only occur for transactions that were executed and succeeded.
- Atomicity and isolation: each transaction should appear to execute atomically and in some serial order consistent with executed state updates; concurrent executions must not violate serial semantics.
- History bounds: the number of recorded events in the observable history never exceeds the specified bound.
- Liveness (bounded progress): when the node is able to execute a pending request, it eventually produces the corresponding execution and response (unless prevented by the bounded-history constraint), and committed-status notifications eventually appear for committed transactions.
- Invariant: the recorded state and history remain consistent (no dangling references, well-formed event entries).

Do not prescribe implementation details such as specific variables, control-flow labels, or a particular step-by-step algorithm; instead, specify the behaviors, allowed transitions, and the above properties to be verified.
