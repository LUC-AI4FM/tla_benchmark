Specify a distributed transaction processing system for a small replicated key-value store with two keys and three clients. Model clients that perform read and write transactions on subsets of keys; some clients use optimistic concurrency and some use pessimistic locking. The system must support transactions that read a consistent snapshot and write updates atomically: a committed transaction must make all its writes visible together; an aborted transaction must leave state unchanged. Reads by a transaction should reflect either the latest committed values at its start or, for optimistic clients, may detect conflicts and abort. Pessimistic clients must acquire exclusive locks on the keys they will write before reading and hold them until commit or abort, preventing concurrent conflicting commits. The model should include a notion of primary replica assignment per client for coordinating writes, and message-passing between replicas and clients for lock requests, read requests, write proposals, votes, and commit/abort decisions. Key safety properties: (1) atomicity of transactions, (2) serializability (every history is equivalent to some serial execution of committed transactions), (3) absence of lost updates (writes from committed transactions are not overwritten by later commits in a way that loses those effects), and (4) proper use of locks so that pessimistic clients prevent conflicting concurrent commits. Include progress assumptions: nonfaulty clients and primaries eventually make progress (no permanent deadlock), and messages are eventually delivered.
