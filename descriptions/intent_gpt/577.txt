Specify a distributed ledger system that supports multiple nodes maintaining branches of the ledger and handling read/write transactions. The model should represent multiple nodes that can independently accept transactions, execute reads that observe previously committed transactions, and communicate commit status so that transactions become visible across nodes. The system must allow transactions to be proposed, processed, and either committed or not; committed transactions must be durable and visible to later read operations according to an ordering consistent with commits. Reads may query a node’s local branch and must return a set of observed transaction identifiers that reflect a prefix of the committed history available at that node at the time of the read. The model should permit starting from an initial condition where some transactions are already committed and visible on one or more branches. Correctness properties to guarantee: safety — once a transaction is reported committed, its effects are never lost and subsequent reads that observe that commit must not contradict it; monotonic visibility — any read that occurs after another read or commit on the same node must observe at least the same set of committed transactions (no rollback of observed commits); and consistency across nodes — if a transaction is committed systemwide, all nodes eventually make it visible to reads (liveness: eventual visibility). Additionally ensure that reads return observed sets that are internally consistent with the ordering of committed transactions (no observing a later commit while missing an earlier committed predecessor). The specification should abstract away protocol internals and focus on the observable behavior and these properties.
