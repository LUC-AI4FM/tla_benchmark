Specify a model of a key-value database that supports multi-operation transactions with snapshot isolation semantics. The model should describe clients opening transactions, reading and modifying a private snapshot, aborting, and committing. A transaction’s reads and writes operate on a snapshot taken when it begins; writes produced by a transaction are not visible to other transactions until the transaction successfully commits. Commits must be serialized by checking for write-write conflicts: a transaction may commit only if none of the keys it wrote were concurrently written (and committed) by another transaction in the interval between its snapshot and its commit. If two concurrent transactions write the same key, at most one may succeed; the other must be prevented from committing and may either abort or be retried. Transactions that write to disjoint key sets should be able to commit concurrently without interfering with one another.

Model the lifecycle of transactions (open, perform reads and writes on snapshot, commit, abort), the store state, per-transaction snapshots and per-transaction write-sets. Provide invariants ensuring type-correctness of state components and that closed/aborted transactions leave no leftover per-transaction state. Specify safety properties: snapshot isolation (reads see the snapshot taken at open), no lost updates for non-conflicting transactions, and write-conflict detection forbidding both concurrent writers of the same key to commit. Also state liveness goals informally: progress for non-conflicting transactions (they can commit) and the ability to abort or retry conflicting transactions.
