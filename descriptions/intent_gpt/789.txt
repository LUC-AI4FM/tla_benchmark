Specify a transactional key-value store that supports concurrent transactions, multi-key reads and writes, and atomic commit or rollback. The model should treat keys and values as abstract finite types and represent transactions as distinct identifiers. The system must allow opening a new transaction, performing adds, updates, and removes of keys within a transaction, and then either closing (committing) the transaction or rolling it back. Committing a closed transaction must make its written changes visible in the global store atomically; rolling back must discard all its tentative changes. Reads within a transaction must see that transaction’s own writes and either a consistent snapshot of the global store taken when the transaction opened or a well-defined isolation view; non-transactional reads must see the committed global state. The model must allow transactions to overlap in time and must ensure that one transaction’s tentative writes are not visible to other transactions until commit. Specify invariants expressing type correctness, that transactions maintain lifecycle constraints (opened → operations → closed/rolled back → no further ops), and that commits preserve atomicity (no interleaving partial commits) and durability of committed updates in the global store. State safety properties: absence of lost updates, no writes by closed/rolled-back transactions, and preservation of key domain. Also require a temporal property that the invariants hold invariantly (always).
