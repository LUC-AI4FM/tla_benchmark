Specify a high-level TLA+ model of a proof-of-stake-style blockchain protocol as seen by a light client, focusing on validator sets, block headers, commits, time, and faults. The model should represent a linear sequence of block headers with monotonically increasing heights and timestamps, each header carrying the validator set for that height, the next-height validator set, and the set of committers for the previous block. The system must allow some nodes to be faulty (Byzantine), where the set of faulty nodes is non-decreasing over time.

The specification must capture these requirements and correctness properties:
- Safety assumptions: for any recent block within a global trusting period, the correct (non-faulty) validators for that block must possess >2/3 of total voting power; equivalently, faulty nodes must never control ≥1/3 of voting power for any header that remains within the trusting period.
- Liveness-like constraints: each block’s commit set must include votes from >2/3 of that block’s validator set, and timestamps strictly increase but not by more than the trusting period between consecutive blocks.
- Time and trust: define a trusting period relative to header timestamps; headers older than the trusting period are not trusted by the light client.
- Byzantine behavior modeling: allow faulty nodes to produce or sign headers and commits arbitrarily; allow a header to appear that is only signed by faulty nodes.
- Fault progression: faults may only increase over time; allow the model to enter a “faulty zone” where the safety assumption does not hold.
- Utility properties to verify: detect whether the blockchain is currently within the trusting period for a given header, check whether a header has sufficient (>2/3) commit support, and assert that the global fault assumption holds for all headers in the trusting window.

Do not prescribe an implementation; instead, specify the abstract state, transitions for advancing time and adding faults, and the invariants and temporal properties that the light client relies on to accept headers safely.
