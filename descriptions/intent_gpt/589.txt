Specify a concurrent transactional storage system that manages a single table with multiple keys and multiple clients. The system should allow each client to perform transactions that read, write, and commit changes to one or more keys. Transactions may overlap in time and can conflict when they access the same key(s). The model must capture start, read, write, abort, and commit behaviors, including automatic rollback on abort and ability to retry or restart transactions. It must model partial failures and recovery: a transaction that fails before commit must not leave partial changes visible to others, and committed transactions must make their effects durable and visible to subsequent transactions.

Require serializability: the effect of concurrent committed transactions must be equivalent to some serial order. Require atomicity: each transaction’s updates are either all visible after commit or none are visible after abort. Require isolation: transactions must not observe intermediate states of other active transactions. Require consistency of per-key values according to user-specified invariants (e.g., uniqueness or monotonicity constraints). Include fairness assumptions that prevent livelock, ensuring that every transaction eventually commits or aborts under reasonable scheduler progress. The specification should be parameterized by number of keys and clients so safety and liveness properties can be checked under different concurrency levels.
