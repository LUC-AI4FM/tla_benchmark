Model a light-client protocol that fetches and verifies blockchain headers from a set of validators, some of which may be Byzantine. The model should describe how the client progresses from an initial trusted header at a low height to a target header at a higher height by repeatedly requesting headers (either directly or via skip/optimistic probes), validating commit signatures, and updating its latest verified header. Include the possibility of faulty validators that may equivocate, withhold signatures, or provide conflicting headers; allow the fraction of faulty validators to be specified. Capture clock behavior: the client has a local clock that may drift relative to a reference clock, and timeouts and trusting-period checks must use this local time. The protocol must support retrying, fetching intermediate headers when direct jumps are not safely verifiable, and distinguishing between headers that are valid, invalid, or unverifiable given current evidence.

Specify safety and liveness properties:
- Safety: the client must never accept a header that contradicts a previously accepted header (i.e., commit to conflicting chains) and must only accept headers if the signed commit satisfies the trust rules (e.g., sufficient non-faulty voting power, not expired).
- Liveness: if a correct majority (or required quorum) of validators are non-faulty and the network eventually delivers messages, the client must eventually verify the target header within the trusting period.
- Time-related invariants: verification decisions must respect trusting-period and clock-drift assumptions; the client must not accept headers whose trust can be undermined by expired validator sets or clock inconsistencies.

Also specify observables for monitoring (previous verified state, verdicts, probe counts) so that external checks can assert whether the client behaved correctly and whether faulty behavior was detected.
