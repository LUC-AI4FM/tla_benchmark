Specify a formal model of a cluster worker agent and its interaction with a central scheduler that manages task lifecycles. The model should represent: tasks with identifiers, assigned nodes, desired states, and observed states; a worker node that runs containers corresponding to tasks and tracks container lifecycle states (running, terminating, complete, failed); and the rest of the system (scheduler and other nodes) that creates, updates, and removes tasks. The worker must be able to: start containers to reach a task's desired state; advance task state through legal progressions (assigned → accepted → preparing → ready → starting → running) only when connected to the scheduler; initiate and complete shutdowns when the scheduler stops mentioning a task or requests its shutdown; report container state back to the scheduler so the scheduler's view of task states remains consistent with reality; reject tasks before they reach running; mark tasks orphaned when the worker is disconnected long enough; and handle abrupt events such as container crashes and node reboot (which terminates running containers). The environment must be allowed to create, update, and remove tasks, and to mark nodes up/down.

Specify safety properties: task state transitions must follow only allowed transitions; the worker must never report impossible state combinations; containers must respect desired-state semantics (not run past desired_state); and tasks should only be removed after reaching a terminal state. Specify liveness properties: if progress is possible (node connected and transitions allowed) the worker eventually makes progress toward desired states; the worker eventually synchronizes container state with the scheduler's store; and any requested shutdowns eventually complete. Also require that the concrete worker/container-level model refines an abstract worker-specification that only observes task states in the scheduler.
