Model an isolation-detection component for a blockchain full node that, upon receiving evidence from a light client that two peers disagree on a block at a given height, identifies a set of validators considered attackers. The model should represent a set of validators (some faulty, others correct), a reference (common) block agreed by peers, and a conflicting block reported by a light client. The system must accept any valid evidence the light client would certify, and it must consider the possibility that the safety threshold of the protocol is violated (more than a third of voting power may be Byzantine).

Specify the isolation logic abstractly: given the reference block, the conflicting block, and possibly commit rounds, the component must produce a non-empty set of suspected attackers when it transitions out of the initial state. The specification must not assume particular implementation steps but must express the allowed cases that justify classifying validators as attackers (e.g., invalid header fields, conflicting commits, same-round equivocation, or liveness/amnesia scenarios where enough validators in a quorum are faulty).

State the essential correctness requirements as invariants:
- Any produced attacker set must have aggregate voting power strictly greater than one third of the validators at the conflict height (detection completeness).
- Every validator in the produced attacker set must actually be faulty (detection accuracy).
Also require that evidence accepted by the model is consistent with the light client verification API used by the full node.
