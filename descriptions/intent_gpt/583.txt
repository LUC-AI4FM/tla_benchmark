Specify a formal model of a replicated ledger service that supports multiple views (leader epochs) and can experience view changes that roll back uncommitted transactions. The model should represent a collection of ledger branches (one per view) and a single authoritative commit sequence number that advances when transactions are durably committed. The system must allow the following behaviors:

- Clients submit read/write transactions and receive status responses (committed or invalid). A committed response must correspond to a particular view and sequence number that has been durably recorded at the commit sequence.
- View changes (leader elections) can truncate the current branch by discarding some suffix of uncommitted entries and create or advance to a new view. Such truncations must never remove entries that are already committed.
- It must be possible for the system to reply that a transaction is invalid if the transaction’s recorded view/sequence cannot possibly become committed (either because the commit sequence has moved past that sequence with a different view, or because the current view is strictly greater and will prevent that sequence from being committed under the older view).
- The model should capture history of responses so that every response can be related to ledger state and view information.

Specify the safety properties to check: no response declares a transaction committed unless it matches the committed view and sequence; no truncation ever discards committed entries; and any declared invalid status is justified by ledger/view state (i.e., it is impossible for that transaction to later become committed). Also specify liveness goals about progress of commit sequence under fair scheduling so commits can advance when proposals exist.
