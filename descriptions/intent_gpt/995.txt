Specify a distributed resource allocator system with multiple clients and a finite set of reusable resources. The system must allow clients to request arbitrary subsets of resources, to receive allocations that may be partial, and to return subsets of resources they hold. Clients may only issue a new request when they currently have no outstanding request and hold no resources. Communication between clients and the allocator is asynchronous: requests, allocation grants, and returns are sent as messages and may be delayed arbitrarily, but messages are not duplicated or corrupted.

The allocator must keep track of outstanding client requests and of currently allocated resources, and it must repeatedly build and extend schedules that determine an ordering of clients to be served. An allocation decision may allocate resources to a client only if those resources are not claimed by any client earlier in the chosen schedule. The allocator is allowed to satisfy a request incrementally (send partial allocations over time) and clients may return resources even before their full requested set is satisfied, but clients are required to eventually return any currently held resources once their outstanding request has become fully satisfied.

Formalize the state and transitions so that the following safety and liveness properties can be verified:
- Mutual exclusion of resource holding: no two distinct clients ever simultaneously hold the same resource.
- Requests and allocations are accounted for across the asynchronous network so the allocator’s view and clients’ local views remain consistent.
- If a client’s request becomes satisfied (every requested resource has been allocated and received), that client will eventually return all resources it holds.
- If a resource is requested by a client, the client will eventually obtain that resource (subject to scheduler fairness).
- The allocator eventually schedules waiting clients and eventually issues allocations when they are possible.
- All messages sent are eventually delivered.

Model these behaviors abstractly (without prescribing a particular implementation algorithm) and state the invariants and fairness assumptions needed to prove the properties above.
