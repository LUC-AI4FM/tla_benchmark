Specify a model of a single-node transaction processing service that supports both read-write transactions and read-only transactions. The model should describe a sequential history of requests and responses recorded by the node, where read-write transactions may mutate the node’s internal ledger state and read-only transactions observe a snapshot of a ledger branch without modifying it. The system must accept new read-only requests, deliver responses for previously received read-only requests exactly once, and record for each read-only response the observed sequence of committed transactions and an identifier for the ledger snapshot that was read.

The specification must ensure that:
- Read-only requests are eventually responded to when a valid snapshot exists.
- Read-only responses accurately reflect some consistent prefix or branch snapshot of the ledger as it existed at the time of response.
- Read-only responses do not change the ledger state or otherwise interfere with concurrent read-write commits.
- No duplicate responses are produced for the same read-only request.
- The history sequence always records request and response events in order, and response events reference the request identifier they answer.

Also require basic safety properties already expected of the node: the ledger evolves only via valid commit actions, and the model preserves invariants about ledger branch structure and indices used to identify snapshots. Liveness properties should assert eventual handling of read-only requests under fair scheduling.
