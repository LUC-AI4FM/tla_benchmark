Specify a TLA+ model of a Tendermint light client algorithm that verifies a target block header given a single initially trusted header. The model should represent (1) a blockchain oracle that maintains authentic block headers, their commits, and a notion of faulty validators, (2) a light client that interacts with a full node (primary) to fetch light blocks and that maintains a local store of fetched blocks with per-height statuses (verified, unverified, failed), and (3) clock sources: a global reference clock and the client's local clock that may drift within a bounded envelope.

The light client must try to verify the header at a target height by iteratively fetching candidate headers and running a verification routine that can return success, not-enough-trust, or an error. It must allow scheduling which next height to probe, update stored blocks and statuses, advance the latest verified header on success, terminate with success when the target is verified, and terminate with failure upon unrecoverable verification errors. Fetch responses may either be truthful copies from the blockchain (if the primary is correct) or arbitrary blocks consistent with signature rules (if the primary or some validators are faulty, subject to a maximum faulty ratio).

Specify these safety and liveness requirements to be checked:
- Correctness: any header marked verified in the client store must equal the blockchain header at that height (no false verification).
- Chain-of-trust: on successful termination, verified headers must form a proof chain: for any two stored verified headers, either there is an intervening verified header or the later header is validatable from the earlier, unless the earlier is outside the trusting period.
- No failed blocks on success: if the algorithm finishes successfully, no stored block is in failed state.
- Termination under good conditions: if the initial trusted header is still within its trusting period and the primary is correct (and clocks respect the drift bounds), the client must eventually finish with success.
- Precision: if the algorithm finishes with failure while the trusted header is still within its trusting period, then either the full node lied about a fetched block or its commits, or the trusted header genuinely expired.

Do not prescribe implementation details of scheduling, storage updates, or verification internals beyond the abstract interactions, and parameterize the model by trusting period, clock drift bounds, faulty validator ratio, trusted and target heights, and whether the primary is correct.
