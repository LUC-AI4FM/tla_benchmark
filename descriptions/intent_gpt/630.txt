Specify a TLA+ model of a light-client trust-detection and evidence-creation subsystem used by a client that tracks a blockchain via validator-signed headers. Model the system at the level of abstract events (message receives, local time progression, verification attempts, and evidence creation), not implementation code. The model should include a set of validators, some subset of which may be faulty, a reference blockchain that produces sequential blocks with headers and validator sets, and a light client that stores a small set of fetched headers and maintains a local notion of trusted height. The client must regularly verify higher headers against trust anchored at a trusted height using attacker-resilient verification rules that tolerate up to the allowed faulty fraction. When conflicting headers or inconsistent signatures are observed, the client must be able to construct and output evidence that a peer is equivocated or provided invalid signatures. Specify time and clock drift parameters so verification can expire after a trusting period and so local and reference clocks may differ.

Key correctness properties to guarantee:
- Safety: The client never accepts (marks trusted) a header that is inconsistent with the reference blockchain unless more than the tolerated fraction of validators are faulty.
- Liveness: If the reference chain advances honestly and enough correct validators sign, the client eventually succeeds in verifying and advancing its trusted height within the trusting period.
- Evidence soundness: Whenever evidence is produced, it is valid (it proves a violation: conflicting signed headers or invalid signatures) and would be accepted by an honest verifier.
- Expiry: The client does not rely on trust anchors older than the trusting period (i.e., it must refuse to verify using expired trusted heights).
- Fault tolerance: The model must capture the tolerated faulty ratio and ensure that safety holds when at most that fraction of validators are faulty, and that safety can be violated only when more than that fraction are faulty.

Include nondeterministic behaviors for message delays, adversarial choices for faulty validators, and local clock drift.
