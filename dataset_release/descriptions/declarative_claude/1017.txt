The VoucherTransfer module specifies the transfer of vouchers between holders using a Two-Phase Commit protocol, based on the "Transfer" operation from RFC 3506. Three constants parameterize the model: a set of vouchers V, a set of Source Voucher Holders SH (current owners wishing to transfer), and a set of Destination Voucher Holders DH (recipients waiting to receive). The seven state variables track the state of each voucher and its lifecycle machine (both initially fixed at "valid" and "working"), the per-holder states for SH (holding, prepared, transferred, aborted) and DH (waiting, prepared, holding, aborted), the Voucher Transaction Provider (VTP) state (init or done), the set of prepared acknowledgments received by the VTP, and the global message set.

The VTP coordinates transfer by collecting "Prepared" messages from all SH and DH members before broadcasting either a "Transfer" or "Abort" decision. Source holders can spontaneously prepare or abort, and respond to Transfer or Abort broadcasts. Destination holders behave symmetrically, transitioning from waiting to prepared, holding, or aborted. The safety invariant VTPConsistent asserts that no source holder reaches "transferred" while any destination holder is "aborted," and vice versa, preventing conflicting outcomes. The temporal specification VTPSpec is the initial state conjoined with a stuttering-tolerant next-state relation over all variables, with no fairness conditions. The model is checked with three vouchers and three holders on each side, verifying VTPTypeOK and VTPConsistent as invariants with deadlock checking disabled. The module also declares a refinement theorem asserting that VTPSpec implements the VoucherLifeCycle specification VSpec, though the configuration comments note this refinement does not hold.
