The module models a single-client read-write protocol against a cloud database (styled after Azure Cosmos DB) that supports five configurable consistency levels. The system has two kinds of processes: one `cosmosdb` process representing the cloud (node 0) and one or more `client` processes (constrained by the assumptions to exactly one client), communicating over FIFO channels indexed by process ID.

The `cosmosdb` process maintains a sequence `Database` initialized to `<<0>>` and dispatches incoming messages by type. Write requests append the new value and return an acknowledgment carrying the latest sequence position. Read requests are handled according to the consistency mode: Eventual and Consistent_Prefix may return any existing database entry; Session constrains the reply to entries at or after the client's last-known session index; Bounded_Staleness restricts replies to within `K` entries of the end; Strong always returns the latest entry.

Each client repeatedly performs `MaxNumOp` read-then-write cycles. It sends a read request tagged with the configured `Consistency` level and its current session token, receives a reply, records the returned value in `chistory`, then sends a write of `v+1` and awaits an acknowledgment that advances the session token.

Five named invariants capture the consistency guarantees for client 1. `Eventual` and `Consistent_Prefix` assert the last read value exists somewhere in the database. `Session` asserts (when a write is about to be issued) that the last read came from an index at or after the session token. `Bounded_Staleness` asserts the read came from within the last `K` database positions. `Strong` asserts the last read is exactly the most recent database value. The temporal specification is a standard safety-only `Init /\ [][Next]_vars` with no fairness or liveness properties.
